# localagent-box v1

Narrow localagent-box to batch runs (plus review), and make those runs trustworthy. The host owns verification, git, credentials and limits. The model is used where judgement is needed. Each run leaves behind lessons that make the next run cheaper.

**Status:** Planned

**Related:** [one-shot-batch-options.md](../one-shot-batch-options.md), [review-autofix.plan.md](./review-autofix.plan.md), [agent-bootstrap.plan.md](./agent-bootstrap.plan.md), [../../SECURITY.md](../../SECURITY.md)

---

## Goals

1. Batch and review are the only run modes. Interactive and loop modes are removed.
2. A batch run is only reported as successful when host-run checks pass, not merely when files changed.
3. Failed checks get a bounded number of repair attempts. After that, a person is notified with enough context to act.
4. Credentials are not readable from the agent's workspace or transcripts.
5. Agents cannot perform host-owned operations (commit, push, merge, release) or act outside the workspace.
6. Every model-produced artefact the host consumes is validated against a schema.
7. Retrospectives can be run on demand over completed runs, and recurring mistakes surface as suggested instruction changes.
8. Runs have time and spend ceilings that stop cleanly without losing finished work.

## Non-goals for v1

- A container per run, or running the full application stack inside the workspace.
- Splitting a task into multiple steps within a run. Larger work is split into separate batch runs by the caller.
- Running more than one model step in parallel within a single run.
- Applying lessons to prompts automatically. A person approves every instruction change.
- Running retrospectives automatically at the end of each run. They are triggered on demand from settings or the API.
- An egress proxy or network allowlist.
- A migration path for existing interactive or loop agent records beyond read-only display.

---

## Principles

| Principle | Meaning |
|-----------|---------|
| One run shape | A run is a task in, a verified branch (and optionally a PR) out. Follow-up work is a new batch run on the same branch. |
| Host owns the mechanics | Build, test, commit, push, PR creation, CI polling and GitHub thread resolution are plain code. Agents never run them. |
| Model for judgement only | The model implements, repairs, reviews and reflects. It does not decide whether a check passed. |
| Two attempts, then a human | Every repair loop is capped at two attempts. Escalations include what each attempt changed and why it failed. |
| Machine failures are not code failures | Out-of-memory, disk-full and timeouts never trigger a repair turn. |
| Stop, don't abort | Hitting a ceiling commits and pushes completed work, then reports. |
| Validate everything the host reads | Model output goes through a schema with one corrective retry. |
| Instructions are earned | Each rule in agent guidance should trace back to a real failure. |

### Phase 1: Verification and repair (highest priority)

**1.1 Post-run verification.** After the agent session ends, run the repo's configured checks on the host. Record the exit code, duration and truncated output on the agent record.

- Extend `environment.json` / `.localagent-box/config.json` with optional `build`, `lint` and `test` commands. Keep `verifyCommand` as the shorthand.
- Read these commands from the base branch, as review config already is, so a change cannot weaken its own checks.
- A run with no configured checks behaves as today, and the UI and PR body say "unverified".

**1.2 Repair loop.** On check failure, send the failure output to the same OpenCode session as a repair turn. Re-run the checks after each attempt.

- At most 2 repair attempts (configurable per repo, range 0–3).
- Classify failures first. OOM, disk-full, command-not-found and timeouts fail the run immediately with a "machine" reason.
- When attempts run out, mark the run `needs-attention`. Push the branch, but do not open a PR unless the repo opts in to draft PRs on failure.

**1.3 Completion gate for zero-change runs.** If the agent reports success but changed no files, send one follow-up turn asking it to finish the task or explain why no change is needed. Store that explanation on the run. This closes the auto-retry and completion items in `one-shot-batch-options.md`.

**1.4 Honest PR test plan.** The host writes the "Test plan" section of the PR body from the checks it actually ran (command, result, attempts). The LLM-generated body supplies only the summary.

**1.5 Escalation content.** `agent.failed` / `needs-attention` webhooks and UI include the failing check, a diff summary for each attempt, and the agent's stated reasoning for each attempt.

### Phase 2: Credentials and permissions

**2.1 Remove the token from the remote URL.** `buildAuthenticatedCloneUrl` currently writes `x-access-token:<token>` into `.git/config` via `git remote set-url`, which any agent shell can read.

- Clone and push with a per-command credential (`-c http.extraheader=...` or a host-side credential helper) and leave `origin` as the plain HTTPS URL.
- Add a test asserting `.git/config` contains no token after workspace setup and after push.

**2.2 Redact on write.** Apply redaction to every persisted transcript, log line and event before it reaches disk or SSE. Cover GitHub tokens, provider API keys (including OAuth-style tokens) and database connection strings. Centralise the patterns in one module with tests.

**2.3 Narrow the default permission policy.** Replace allow-all auto-approve with broad allows plus explicit denies:

- Deny `git commit`, `git push`, `git stash`, `git reset --hard`, `git checkout` of other branches, and `git -C` outside the workspace. Read-only git stays allowed.
- Deny `gh pr merge`, `gh release`, `docker`, and edits outside the workspace (`external_directory`).
- Keep `question` denied (all runs are now unattended).
- Repos can extend the deny list but not shrink it.

**2.4 Refs guard.** Snapshot branch refs and HEAD before each agent turn. After the turn, if the agent moved refs, restore them (keeping file changes) and log a warning. If they cannot be restored, stop the run. This complements the existing start-commit tracking.

**2.5 Safe host reads.** When the host reads files written by an agent (review findings, artefacts, retros), refuse symlinks and paths outside the agent data directory.

### Phase 3: Structured output

**3.1 Schemas for model artefacts.** Define zod schemas for PR content (`{title, body}`), the zero-change explanation (1.3) and the retro (4.1). Generate JSON Schema from them for prompts.

**3.2 Corrective retry.** On validation failure, send the validation errors back once. If it fails again, fall back to the existing template (PR body) or fail the step (retro).

**3.3 Self-validation.** Provide a small validate command the agent can run against its own artefact before finishing. It uses the same code path as the host.

### Phase 4: Learning from runs

**4.1 On-demand retrospectives.** Retros are not run automatically. They run after the fact from saved run artefacts, so they need no live session or workspace. This uses the same pattern as PR content generation (`agent.service.ts`, which already builds content from saved messages, events, logs and the diff).

- **Inputs, built in code before any model call:**
  - The task prompt, the outcome, check results and repair attempts.
  - The diff stat.
  - Assistant messages.
  - A digest of `events.jsonl`: failed `tool.end` calls, `permission.requested`, `error` events and refused commands. Drop `assistant.delta` noise.
  - Everything is redacted with 2.2 before it is sent.
- **Capture at completion:** store the diff stat (and a truncated patch) on the agent record when the run finishes, so retros still work after workspace cleanup (7.2).
- **Execution:** a host job that makes a direct model call with the retro model (5.1), not a coding agent. It has no workspace and no tools. Jobs run through the existing queue with low priority.
- **Output:** a schema-validated record (3.1) covering:
  - What the task was and the outcome.
  - Mistakes made, such as refused commands, failed checks or wrong assumptions, each with a category.
  - Instructions that were missing or wrong.
  - A suggested change: the target file (`AGENTS.md`, `.localagent-box/config.json`, tool instructions) and proposed text.
  - Records are appended to `DATA_DIR/retros.jsonl` with repo, agent id, retro model, retro prompt version and cost.
- **Idempotent:** a run that already has a retro for the current retro prompt version is skipped unless `force` is set. Bumping the prompt version makes old runs eligible again.

**4.2 Trigger from settings.** Add a Retrospectives section to the Settings page:

- Select scope: a repo (or all repos), a date range or "since last retro", and outcome filters (failed / needs-attention only, or all).
- Show the number of eligible runs and the estimated cost before starting.
- A Run button starts a retro batch, with progress shown in place.
- Retro model and maximum runs per batch are configured here.

**4.3 Trigger via API.**

- `POST /api/v1/retros`: body `{ repoId?, since?, until?, agentIds?, outcomes?, force? }`. Returns a retro batch id and the eligible run count. Auth required.
- `GET /api/v1/retros/:batchId`: status and per-run results.
- `GET /api/v1/retros?repoId=&since=`: list retro records.
- `POST /api/v1/agents/:id/retro`: shortcut for a single run (also used by a "Run retro" action on the session page).

**4.4 Lessons view.** Add a UI page that groups retro mistakes by repo and category over a time window, ranked by frequency and cost. Each grouped item shows its suggested change, and the page links to the settings trigger when there are runs without retros.

**4.5 Suggest-a-change PR.** From the lessons view, open a PR against the repo that applies a selected instruction change. A person reviews and merges it. Nothing is applied automatically.

**4.2 Lessons view.** Add a UI page that groups retro mistakes by repo and category over a time window, ranked by frequency and cost. Each grouped item shows its suggested change.

**4.3 Suggest-a-change PR.** From the lessons view, open a PR against the repo that applies a selected instruction change. A person reviews and merges it. Nothing is applied automatically.

**4.6 Seed the tool instructions from real failures.** Restructure `config/opencode-tool-instructions.md` into:

- A "refused → use instead" table for host-owned or blocked operations (git commit/push/stash, foreground `sleep`, `pkill -f` patterns that match the agent's own shell, `cd` outside the workspace).
- A "rules that keep being relearned" section, where each rule cites the failure that produced it.

Remove the duplicated copy in `src/services/opencode-config.ts` so the file is the single source. Add a test that fails if a copy reappears.

### Phase 5: Limits and cost

**5.1 Per-role models.** Allow separate model settings for implement, repair, retro and PR-content steps (global default, repo override). Repair, retro and PR content default to a cheaper model.

**5.2 Run ceilings.** Add per-run limits for wall-clock time and estimated spend (global, repo override). Check them between turns. On breach, stop the session, commit and push completed work, mark the run `stopped-ceiling`, and notify.

**5.3 Zero-cost guard.** If a spend ceiling is set but every model call priced at $0, fail fast with a configuration error naming the unpriced model.

### Phase 6: Run state and follow-ups

**6.1 Single progress file.** Maintain one `progress.md` (plus `progress.json`) per run, rewritten in full on every state change: current step, checks run, attempts, ceilings, decisions. It is readable as a whole at any point and is the source for the UI summary.

**6.2 Resume.** `POST /api/v1/agents/:id/resume` continues a stopped or needs-attention run on the same branch from `progress.json`, without re-running completed steps. This differs from retry, which starts from a fresh workspace.

**6.3 PR comment follow-ups.** This replaces interactive mode for course correction. Watch PRs opened by localagent-box for `/localagent <instruction>` comments. Accept them only from the repo's configured maintainers and never from bots. Each one runs a follow-up batch on the same branch, with Phase 1 checks.

**6.4 Review polling semantics.** When waiting on a PR, treat "green CI with no review" as unreviewed, not approved. Fix-agent prompts require every assigned finding to be either fixed or explicitly answered.

### Phase 7: Operational hygiene

**7.1 Webhook retries.** Retry outbound webhooks with exponential backoff (3 attempts) and log the final failure.

**7.2 Workspace retention.** A periodic sweep removes workspaces for completed, failed or cancelled runs older than a configurable age (default 7 days). Agent records and logs are kept.

**7.3 Docs cleanup.** Fix dead references (`docs/lessons.md`, `docs/agent-session-startup-flow.md`, `./.agents/skills`). Update the OCR version in `code-review.md` to match the Dockerfile. Remove tracked artefacts (`.npm-node/npm.cmd`, `docs/pr-review-output.json`).

## Sequencing

| Order | Items | Rationale |
|-------|-------|-----------|
| 1 | 0.1–0.5 | Shrinks the codebase before anything else is built on it |
| 2 | 2.1, 2.2 | Small, security-relevant, no behaviour change for users |
| 3 | 1.1–1.5 | Largest quality gain; defines the run states later phases build on |
| 4 | 2.3, 2.4, 4.6 | Permissions and instructions are tuned together, since denies need "use instead" guidance |
| 5 | 3.1–3.3 | Needed before the retro can be trusted |
| 6 | 4.1–4.5 | Learning loop, on demand |
| 7 | 5.1–5.3 | Cost control and per-role models |
| 8 | 6.1–6.4, 7.x | Follow-ups and hygiene |

## Run states after v1

| State | Meaning |
|-------|---------|
| `queued` / `running` | Unchanged |
| `verifying` | Host checks running |
| `repairing` | Repair turn in progress (attempt n of max) |
| `completed` | Checks passed (or none configured), branch pushed |
| `needs-attention` | Repair attempts exhausted; branch pushed, person notified |
| `stopped-ceiling` | Time or spend ceiling hit; completed work pushed |
| `failed-machine` | Environment failure (OOM, disk, timeout); not sent to repair |
| `failed` / `cancelled` | Unchanged |
