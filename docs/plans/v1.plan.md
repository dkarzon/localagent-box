# localagent-box v1

Narrow localagent-box to batch runs (plus review), and make those runs trustworthy. The host owns verification, git, credentials and limits. The model is used where judgement is needed. Each run leaves behind lessons that make the next run cheaper.

**Status:** Planned

**Related:** [one-shot-batch-options.md](../one-shot-batch-options.md), [review-autofix.plan.md](./review-autofix.plan.md), [agent-bootstrap.plan.md](./agent-bootstrap.plan.md), [../../SECURITY.md](../../SECURITY.md)

---

## Goals

1. Batch and review are the only run modes. Interactive and loop modes are removed.
2. A batch run is only reported as successful when host-run checks pass, not merely when files changed.
3. Failed checks get a bounded number of repair attempts. After that, a person is notified with enough context to act.
4. Credentials are not readable from the agent's workspace or transcripts.
5. Agents cannot perform host-owned operations (commit, push, merge, release) or act outside the workspace.
6. Every model-produced artefact the host consumes is validated against a schema.
7. Retrospectives can be run on demand over completed runs, and recurring mistakes surface as suggested instruction changes.
8. Runs have time and spend ceilings that stop cleanly without losing finished work.

## Non-goals for v1

- A container per run, or running the full application stack inside the workspace. (Consequence: an agent shell can still read files elsewhere on the host filesystem, such as the per-agent OpenCode config holding the provider API key. 2.1 and 2.3 reduce exposure but do not remove it.)
- Splitting a task into multiple steps within a run. Larger work is split into separate batch runs by the caller.
- Running more than one model step in parallel within a single run.
- Applying lessons to prompts automatically. A person approves every instruction change.
- Running retrospectives automatically at the end of each run. They are triggered on demand from settings or the API.
- An egress proxy or network allowlist.
- A migration path for existing interactive or loop agent records beyond read-only display.
- Inbound GitHub webhooks. Anything that watches GitHub polls through the GitHub App.

## Principles

| Principle | Meaning |
|-----------|---------|
| One run shape | A run is a task in, a verified branch (and optionally a PR) out. Follow-up work is a new batch run on the same branch. |
| Host owns the mechanics | Build, test, commit, push, PR creation, CI polling and GitHub thread resolution are plain code. Agents never run them. |
| Model for judgement only | The model implements, repairs, reviews and reflects. It does not decide whether a check passed. |
| Two attempts, then a human | Every repair loop is capped at two attempts. Escalations include what each attempt changed and why it failed. |
| Machine failures are not code failures | Out-of-memory, disk-full and timeouts never trigger a repair turn. |
| Stop, don't abort | Hitting a ceiling commits and pushes completed work, then reports. |
| Validate everything the host reads | Model output goes through a schema with one corrective retry. |
| Instructions are earned | Each rule in agent guidance should trace back to a real failure. |

## How to use the work-item briefs

Each work item below is written so it can be handed to a localagent-box batch run on its own. Paste the shared conventions and the item into the run prompt.

### Shared conventions (include with every brief)

- **Stack.** Server: TypeScript (strict, `noUnusedLocals`, NodeNext) under `src/`. Tests use `node:test` and `node:assert/strict`, live next to the source as `*.test.ts`, and run with `tsx`. No mocking library: inject dependencies by hand, or use real temp git repos. Client: React 19 + Vite under `client/`, with no tests.
- **Verify before finishing.**
  - `npm test`.
  - `npm run build`. This also type-checks test files, so fixtures with removed keys fail here.
  - `npx tsc -p client` whenever `client/` changed. `npm run build --prefix client` does **not** type-check.
- **Line numbers** in the briefs are from commit `71ec0f1`. They will drift as earlier items land, so locate code by the symbol name given and use the line only as a hint.
- **File names that differ from older docs.**
  - Per-run events are `DATA_DIR/agents/<id>/events.ndjson`, not `events.jsonl`.
  - The log file is `DATA_DIR/agents/<id>/worker.log`; the code calls it the log path.
- **Two layers share state.** The worker (child process, `src/domains/agents/worker/*`, `src/integrations/opencode/*`) writes agent records with `updateAgentRecord` (`worker/agent-state-writer.ts`). The server (`src/domains/agents/agent.service.ts`) reacts in `handleWorkerExit`. PRs and webhooks are created on the server from the record, never in the worker.
- **Adding a global setting.** Five places must change, or the setting is silently dropped on save:
  - `AppConfig` and `PublicConfig` in `src/types/index.ts`;
  - `DEFAULT_CONFIG` in `src/services/config-store.ts`, because `saveConfig` whitelists its keys;
  - `toPublicConfig`;
  - validation in `PUT /api/v1/config` (`src/routes/config.ts`);
  - the client `AppConfig` in `client/src/api/types.ts`.
- **Adding a repo-level override.** Copy `autoReviewPullRequests`, which goes through these places:
  - `Repo` in `types/index.ts`;
  - `RepoUpdateFields` and the load normalisation in `repo.repository.ts`;
  - validation in `repo.service.ts` `updateRepo`;
  - parsing in `routes/repos.ts`;
  - a resolver like `src/lib/resolve-auto-review.ts` (agent → repo → global → default) with its own test;
  - the UI in `client/src/pages/RepositoriesPage.tsx`.
- **Adding a status.**
  - Server:
    - `AgentStatus` (`types/index.ts`);
    - `TERMINAL_STATUSES` / `BATCH_ACTIVE_STATUSES` / `ACTIVE_STATUSES` (`agent.types.ts`);
    - `BRANCH_WORKER_STATUSES` (`queue-eligibility.ts`);
    - `lib/agent-review-gating.ts`, `lib/resolve-auto-review.ts` and `review-autofix.service.ts`;
    - `sseLockedStatuses` in `session-orchestrator.ts`, otherwise an OpenCode `busy` event overwrites the status with `processing`;
    - `restoreOnStartup` in `agent.service.ts`.
  - Client: the `AgentStatus` union and status sets in `client/src/api/types.ts`, and `agentStatusVariant` / `agentStatusPulse` in `client/src/components/ui/Badge.tsx`.
- **Adding a route.**
  - Handlers use `withErrorHandling` (`lib/error-handler.ts`), plus `readJsonBody`, `sendJson`, `parseUrl` and `decodePathParam` (`lib/http.ts`).
  - Mutating routes call `requireAuth(req, res)` first. Copy `routes/repos.ts`.
  - A new route file is registered in the `routes` array in `src/server.ts`.
  - Throw `validationError(msg)` (`lib/validation.ts`) for a 400.
- **Scope.** Touch only what the brief names. Do not reformat unrelated code. Do not add a dependency unless the brief says so.
- **Status naming.** New statuses use underscores to match existing ones (`awaiting_input`). Write them as `needs_attention`, `stopped_ceiling` and `failed_machine` everywhere, including the client. The run-state table at the end uses these names.

### Brief format

Each item has these parts:

- **Depends on:** items that must be merged first.
- **Context:** what exists today and where.
- **Do:** numbered steps.
- **Don't:** scope fences.
- **Done when:** acceptance criteria and the tests to add.

Decisions taken while expanding the plan are marked **Decision:**. Change them before handing an item out if you disagree.

**0.5 Narrow the mode union, warn on legacy config, protect legacy records.**

- **Depends on:** 0.4.
- **Context:**
  - The union `AgentMode = 'batch' | 'interactive' | 'loop' | 'review'` is defined twice: `src/types/index.ts:266` and `src/lib/validation.ts:135`.
  - `validateAgentMode` (`lib/validation.ts:137-152`) throws `validationError`, which gives a 400.
  - `worker/environment-config.ts:139-151`: `VALID_MODES` validates `setup.runOnModes`. An existing `environment.json` that lists `loop` would start throwing.
  - `services/config-store.ts` `loadRaw` spreads unknown keys into memory and `saveConfig` writes them back, with no warning.
  - `worker/repo-config.ts` `validateRepoConfig` silently ignores unknown keys.
  - Legacy records load fine because `mode` is just a string in `agents.json`. However:
    - `restoreOnStartup` (`agent.service.ts:1429-1445`) uses `BATCH_ACTIVE_STATUSES`, which lacks `awaiting_input`. A legacy interactive record stuck in `awaiting_input` would never be failed, and would block its branch in `queue-eligibility.ts`.
    - `retryAgent` and `allowSuccessors` would happily re-queue a legacy record, which would then run as batch.
- **Do:**
  1. Single source of truth:
     - `types/index.ts`: `export type AgentMode = 'batch' | 'review'` and `export type LegacyAgentMode = 'interactive' | 'loop'`. `Agent.mode?: AgentMode | LegacyAgentMode`; `AgentJob.mode: AgentMode`.
     - `lib/validation.ts` imports the type instead of redeclaring it.
  2. `validateAgentMode`:
     - accepts `batch` and `review`, with null or empty meaning `batch`;
     - for `interactive` or `loop`, throws `validationError('mode "<x>" was removed in v1; use "batch" (follow-ups are new batch runs on the same branch) or "review"')`;
     - otherwise throws `mode must be "batch" or "review"`.
  3. `environment-config.ts`: `VALID_MODES = ['batch', 'review']`. Filter `interactive` and `loop` out of `runOnModes` with a note "ignored removed mode <x>" instead of throwing.
     - Return notes from the loader the way `review-repo-config.ts` returns `notes[]`, and write them with `appendLog` at the call site.
     - Any other unknown mode still throws.
  4. Legacy config keys:
     - In `config-store.ts`, define `LEGACY_CONFIG_KEYS`: `interactiveAutoApprovePermissions`, `interactiveAgentTimeoutSeconds`, `loopAutoApprovePermissions`, `loopAgentTimeoutSeconds`, `loopVerbModels`, `loopDefaultMaxIterations`.
     - In `loadRaw`, drop those keys and any other key not in `DEFAULT_CONFIG`. Log one `logger.warn({ keys }, 'ignoring unknown config keys')`.
     - `saveConfig` then no longer writes them back.
  5. In `repo-config.ts`, collect keys not in `allowedKeys` plus `review`, and return them as a note: `Ignoring unknown keys in .localagent-box/config.json: a, b`.
     - Callers append it to the agent log.
     - Known legacy keys (`interactiveContextPrompt`, `loopContextPrompt`, `checkCommand`) get the same warning, not an error.
  6. Legacy records:
     - Add `isLegacyMode(agent)` in `agent.types.ts`.

**2.4 Refs guard.**

- **Depends on:** 1.0 (`sendTurn` wrapper).
- **Context:**
  - `markRunStart` writes `refs/localagent-box/start`, and `getHeadSha` exists.
  - There are no `for-each-ref` or restore helpers.
  - `finalizeGitChanges` treats agent commits as changes and uses the agent's HEAD when it has committed.
- **Do:**
  1. Add to `git-service.ts`:
     - `snapshotRefs(dir)` returns `{ head: string /* symbolic ref or sha */, refs: Record<string, string> }`. Build it from `git symbolic-ref -q HEAD || git rev-parse HEAD` and `git for-each-ref --format=%(refname) %(objectname) refs/heads refs/tags refs/stash`.
     - `restoreRefs(dir, before, after) → { changed: string[] }`.
  2. Restore algorithm:
     1. If HEAD's symbolic ref differs, run `git symbolic-ref HEAD <before.head>`. This changes only HEAD and leaves the working tree as is.
     2. For the agent branch, if its sha moved, run `git reset --soft <before sha>`. Commits are undone but file changes are kept staged.
     3. Delete refs the agent created with `git update-ref -d`.
     4. Restore refs it moved or deleted with `git update-ref <ref> <sha>`.
     5. `refs/stash`: if one was created, run `git stash pop`. If that conflicts, fail.
  3. In `sendTurn`, snapshot before the turn and diff after it. If anything changed:
     - restore;
     - `appendLog` a warning listing the refs;
     - write an event `refs.restored`.
     - If any restore command fails, throw `RefsGuardError`; the run fails with "Agent moved git refs and they could not be restored".
  4. `refs/localagent-box/start` is never touched by the restore.
- **Done when:** real-temp-repo tests cover each case and assert file content survives:
  - agent commits on the branch;
  - agent creates a branch and switches to it;
  - agent creates a tag;
  - agent stashes.

## Sequencing

| Order | Items | Rationale |
|-------|-------|-----------|
| 1 | 0.1 → 0.6 | Shrinks the codebase before anything else is built on it. Each step keeps the build green. |
| 2 | 2.1, 2.2, 2.5, 7.1, 7.3 | Small, security-relevant or independent; no behaviour change for users |
| 3 | 1.0 → 1.5 | Largest quality gain; defines the run states later phases build on |
| 4 | 2.3 (with spike), 2.4, 4.6 | Permissions and instructions are tuned together, since denies need "use instead" guidance |
| 5 | 3.1 → 3.3, then revisit 1.3's TODO | Needed before the retro can be trusted |
| 6 | 7.2, then 4.1 → 4.5 | Retention must stop deleting records before retros depend on them |
| 7 | 5.1 → 5.3 | Cost control and per-role models |
| 8 | 6.1 → 6.4 | Follow-ups |

Items in the same row can run as parallel batch runs only if they touch different files. 2.1 and 2.2 both touch `github-app.ts` `redactSecrets`, so run them one after the other.

## Run states after v1

| State | Meaning |
|-------|---------|
| `queued` / `running` / `processing` / `completing` | Unchanged |
| `verifying` | Host checks running |
| `repairing` | Repair turn in progress (`repairAttempt` n of max) |
| `completed` | Checks passed (or none configured, shown as "unverified"), or a valid no-change explanation; branch pushed when changed |
| `needs_attention` | Repair attempts exhausted; branch pushed, person notified |
| `stopped_ceiling` | Time or spend ceiling hit; completed work pushed |
| `failed_machine` | Environment failure (OOM, disk, timeout, command not found); not sent to repair |
| `failed` / `cancelled` | Unchanged |
| `awaiting_input` | Legacy interactive records only; never set by v1 |
